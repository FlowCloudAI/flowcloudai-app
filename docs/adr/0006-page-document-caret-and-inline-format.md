# ADR 0006：页面编辑的光标权威与行内格式模型

- 状态：接受；待实现
- 日期：2026-09-21
- 关联：[ADR 0003](0003-page-document-canvas-isolation.md) 的画布隔离与 bridge 协议；[ADR 0004](0004-unified-object-layer-and-asset-scope.md) 的节点规则与层叠顺序

## 背景

Word 式的「待输入格式」（折叠光标处先设定格式、随后输入的文字带该格式）是在画布协议冻结之后补进来的。协议里的选区消息只有 `nodeId / from / to / expected` 四个字段（`src/features/page-document/canvas/protocol/types.ts`），整个 `canvas/` 目录不含任何格式概念；这套状态完全活在宿主侧的 React ref 里。

`1f026b7d`…`6479c7ad` 六次修复之后，症状在三处之间迁移而没有消失：格式退回文本块默认值、候选坐标漂移、候选验收失败、输入期间功能区整组禁用、中文组合输入必然丢格式、快速输入时光标跳进相邻的格式片段。

根因不在某一处实现，而在职责分配：**光标在这套设计里是派生数据而不是状态。** 每次输入都经过「画布乐观改 DOM → 宿主提交内核 → 画布整棵重挂」，光标在这三步里被重新推导三次，而宿主只能拿记住的偏移去和上报的偏移比相等，以此判断「这还是不是刚才那个光标」。偏移恰恰在插入字符、包裹 `span`、整棵重挂这三件事里都会变，所以比相等注定失败。

职责分配的具体表现是：**只有画布知道哪次 DOM 变化是它自己造成的，但画布不知道格式存在；只有宿主知道格式，但宿主分不清「作者移动了光标」和「DOM 被重建了」。** `expectedTypingCaretRef`、`refreshCanvasTextSelection`、`createCanvasSelectionReportGate`、`restoreCanvasResolvedSelection`、`restoreCompositionStart` 五套机制都在事后重建同一个判断，因为做判断所需的因果信息不在它们手里。

## 决策

### 1. 光标与标记集由画布持有

画布持有权威的编辑光标，以及挂在光标上的待输入标记集（stored marks）。`text-selection` 消息增加标记集字段；宿主退回显示与转发，不再用偏移比对推断待输入格式是否存活。

标记集只在画布能亲自观察到的作者手势下清除：目标节点变化、上报为非折叠选区、指针落点、方向键移动光标、组合起点落在别的节点、显式清除格式、退出可视模式。由输入自身引发的重挂与光标恢复一律不清除。

协议校验是严格白名单（`canvas/protocol/validation.ts` 的 `hasOnlyKeys`），新增字段未同步校验会导致整条消息被丢弃而不是丢掉该字段。宿主与画布同属一次构建产物，因此不需要为此提升 `PAGE_DOCUMENT_CANVAS_VERSION`。

### 2. 语义偏移与 DOM 位置的映射必须互逆且边界明确

`locateTextOffset` 与 `semanticOffset` 目前在元素边界上有歧义：前者对子元素用 `remaining <= length` 判断是否下潜，等号成立时也会潜入并落在该元素内部末尾。文档含 `span` 之后，同一个语义偏移落在 `span` 内还是 `span` 外取决于遍历先后。

这两个函数连同 `semanticText`、`semanticLength` 移出 `canvas/runtime/main.ts`，成为独立可测模块；边界归属规则写死并由互逆测试固定。`<br>` 记为一个 `\n` 的既有约定不变。

### 3. 字体功能区读写口径各收敛成一条

读只读光标处的计算值，写只产生行内标记。计算值已经把全局、节点级、行内全部层叠进去，因此功能区显示的永远是「这个字实际长什么样」。原先 `pending ?? inspected ?? block?.value` 的三级回退取消；内核探查不再充当控件可用性闸门，只在目标节点被删或不再是受管组件时禁用。

「清除格式」在待输入态是清空标记让其继承，不是把六个属性显式写成文本块当前值。

### 4. 文本块不持有独立的默认字体格式

`paragraph` 承担的是文本块能力，其字体默认值来自词条级与项目级样式，不由每个节点各带一份。按种类区分的排版（`h1`…`h6` 的字号字重）属于词条级样式，不是节点级规则。

节点级字体规则停止从功能区写入，但保留读取，并在属性任务窗格保留「整块覆盖」入口——行内标记写的是 `style` 属性，无法携带媒体查询，每个文本块各自的响应式字号只能由节点级规则表达，取消该入口就没有替代手段。旧词条里已有的节点级字体规则保留读取，不做迁移。

受管节点规则继续负责盒子属性（内距、背景、边框、布局），这条边界不变。

## 考虑过但不采用

**让内核补丁返回位置映射、宿主持有权威选区并逐补丁映射。** 这是教科书答案，撤销重做的光标定位、查找替换与将来任何多步编辑都能复用同一套映射。不采用的理由是收益要等到真正实现这些功能时才兑现，而代价是内核补丁接口扩面——每种补丁都要给出自己的偏移变换。真的要做撤销光标定位或查找替换时重新评估本条。

**切换格式时立即在光标处写入空 `span`，输入时直接写进该 `span`，光标移走则删掉空 `span`。** 不采用，四条理由：

1. 它没有解决根因。仍然需要宿主状态记住「哪个空 `span` 待清理」，而空 `span` 进入草稿后画布照样整棵重挂，重挂后还要重新找回「属于我的那个 `span`」——多出一个新问题。
2. 内核表达不了。编辑目标只有 `text-range` 与 `component-root` 两种（`domain/kernel/contracts/edit.ts`），前者是语义文本上的 UTF-16 区间，而空 `span` 的语义长度为零，在该坐标系里不占位置，「往这个 `span` 里插入」无法表达，需要新增零宽锚点目标。
3. 空行内元素在 contenteditable 里不稳定。光标无法可靠停在空 `span` 内部，通行做法是塞零宽字符占位再到处剥离；IME 在空行内元素里最容易把组合文字落到 `span` 外面，而中文正是当前最脆弱的路径。
4. 它把一个不是编辑的手势变成真实编辑。点一次色板即产生补丁、草稿转为未保存、进入撤销历史；连续切三次格式再开始输入就是三轮建了又删，而「移走光标即删除」是补偿事务，与撤销历史组合后没有直觉上正确的回退点。

附带一提，Word 在折叠光标处改字体时同样不向文档写入任何内容，插入点格式就是内存状态，因此该方案也不是对齐 Word 的做法。

**取消待输入格式，只保留「先选中再改格式」。** 这会让本文涉及的一整类缺陷立即消失，但与 Office 式编辑体验的既定目标冲突，不采用。

## 影响

- 画布运行时从「无测试」变成必须有测试：`canvas/runtime/` 下其余模块都是从 `main.ts` 抽离后才测得上，本次新增的光标与标记集状态同样必须抽到可测边界。
- 失去每个文本块各自的响应式字号的功能区入口；该能力改由属性任务窗格的「整块覆盖」提供。
- 旧词条里的节点级字体规则继续生效，新写入一律走行内标记，两者由层叠顺序决定优先级，不额外引入合并规则。
