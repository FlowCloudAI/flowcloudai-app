同一份页面，两个引擎，键盘升起后完全不同

两台手机装着完全相同的页面：固定顶栏、内容区、底部输入框、底部 Tab。 按下「呼出键盘」，看它们分道扬镳—— Android 的布局纹丝不动，是「相机」滑走了； iOS 是「画布」本身变矮了。 这一个差别决定了两端要写完全不同的代码。 切到「灵感页（大输入框）」还会露出 iOS 独有的第二条位移——Web 层根本读不到的那条。

操作 键盘收起 · 两端一致
固定顶栏 底部 Tab 输入框（composer） 系统键盘（原生层，不属于 Web 布局） 死区（输入框够不到键盘）

先看一个陷阱：默认状态下，两端症状一模一样

只按「呼出键盘」不开修复，两列的「输入框与键盘的缝隙」都是 108，都被 Tab 占住。光看这一行会以为是同一个 bug， 于是想用同一套代码去修——这正是 2026-08 走过的弯路。

真正暴露差别的是上面两行：Android 的 offsetTop 是 313、顶栏跑到 −273 离屏； iOS 的 offsetTop 是 0、顶栏稳稳停在 40。 同样的表象，一个是相机移了，一个是画布矮了。 先分清是谁动了，再决定改什么。

Android：布局不动，相机移动

targetSdk 35+ 强制 edge-to-edge 之后，IME 根本不 resize 窗口。 documentElement.clientHeight 恒为 834，每个元素的 getBoundingClientRect() 在键盘升起前后完全相同。

唯一变的是 visualViewport.offsetTop：Chromium 为了露出焦点元素， 把「可见窗口」整体下移。所以顶栏没有被移动，是被移出了取景框。

判断一个元素在不在屏幕上，正确公式是 rect.top − visualViewport.offsetTop，不是 rect.top。

iOS：画布变矮，元素被迫上移

WebKit 直接把布局视口缩短了：documentElement.clientHeight 从 834 变成 521。所有贴着视口底部定位的东西——Tab、输入框—— 会跟着新的底边真的往上跑。

后果是 Tab 停在键盘正上方，把 108 个像素占死。 这就是需求「Tab 不得占用键盘上方空间」在 iOS 上比 Android 难的根本原因： Android 上「屏幕底部」还在 834，iOS 上它已经变成 521 了。

注意 visualViewport.offsetTop 在 iOS 上是 0。 照搬 Android 的平移抵消，在这里什么也不会发生。

换成「灵感页（大输入框）」，iOS 的第二条位移才现形

小输入框那一档会给人一个错觉：iOS 的顶栏一直好好的，好像 只要把 Tab 隐藏，iOS 就天然没问题。换成灵感页就会看到不是这样。

正文 textarea 占了大半屏，WebKit 为了露出它，直接改 WKWebView 外层 UIScrollView.contentOffset，把顶栏顶出屏幕。 关键在于这次位移和 Android 那次完全不是一个性质：

Android 的平移全额写在 visualViewport.offsetTop 里——能读、能算、能抵消， 已上线的方案就是这么做的。iOS 这次位移发生在原生 scroll view 上，Web 层读数全是 0： offsetTop 是 0，scrollY 是 0，rect.top 还是 40， 根 CSS 早就锁死了不可滚动——你连它发生了都不知道。

所以「位移能否被 Web 算出」那一行才是两端难度的真正分水岭。 Android 的问题是能自己修的，iOS 的这条只能上原生桥。 这也是 a781f94 回退时留下的残留问题——高度已经算对了，顶栏照样离屏。

把「预让修复」打开，看 iOS 那一列

预让修复做的事很简单：在 focusin 时把学习到的键盘高度写进 --fc-kb，让输入框提前抬到键盘顶部。 Android 上它同时解决了两件事——输入框贴住键盘（缝隙 = 0）， 而且因为焦点元素不再落在可见区之下，Chromium 没有理由再平移， 顶栏自然留在屏幕上。这是 2026-08-23 已在真机验收的方案。

同一份 CSS 放到 iOS 上会坏得更彻底：WebKit 已经把视口缩短了一个键盘高度， 页面再让一次，就是双重消费——输入框和键盘之间裂开 313px 的死区。 这正是 a781f94 那次回退记录下来的根因。 iOS 必须先知道「WebKit 已经让了多少」，才能决定自己还要让多少。
